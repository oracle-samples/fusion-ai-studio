# Workflow Test Authoring

You are authoring AI Studio workflow tests from a local assistant session. Do not call backend Builder agent APIs for test generation, data generation, JSON repair, or test-data compaction. For judge grading, the default `local` provider uses the local judge request and attach flow; do not call backend Builder APIs yourself in that route. The explicit `--judge-provider remote` route is the supported noninteractive way to ask the configured FA environment to judge semantic results. Unless the user explicitly requests remote judging, never pass `--judge-provider remote` to `run-workflow-test`, `run-workflow-tests`, or any optimization sweep command — this applies regardless of workspace type (legacy or app-package). Never use `npm run` or `npm test` to execute tests or sweeps; always call the CLI binary directly.

For a request to create, edit, record, run, or diagnose a scripted multi-turn workflow test, also read `workflow-conversation-test-authoring.md`. It extends this contract with conversation-specific schema, continuity, recording, replay, judging, and failure rules. Do not apply those rules to ordinary single-turn sync-plan generation.

Use the CLI as deterministic tooling:

1. After any successful workflow create or material edit, finish all node, edge, input, prompt, and metadata changes, validate the workflow, and save or normalize the changed DRAFT once before starting test sync. Then run `aistudio get-workflow-test-sync-plan --file <workflow.wf>`; it is the automatic inventory plus scenario source and includes existing tests plus a ready baseline when available. Never start a sync plan while workflow authoring commands or repairs are still in progress.
2. Do not call `aistudio get-workflow-test-context --file <workflow.wf>` immediately after `get-workflow-test-sync-plan` as a routine step. Call it only when a specific non-judge authoring decision cannot be made from the sync plan output, such as needing exact node input parameter names or output field names. Semantic judge authoring uses the narrower `get-workflow-test-judge-context` flow below.
3. Run `aistudio get-workflow-test-scenarios --file <workflow.wf>` only when you need the raw scenario suggestions separately from the sync plan.
4. Generate one local workflow test definition JSON object when the test needs model-authored assertions, input, rubric, notes, path assertions, or model-generated `testData`. If you write it to disk, use a scratch path such as `.debug/<test-name>-definition.json`, not the final `test/workflows/...` output path.
5. Materialize the source-controlled test with `aistudio do-generate-workflow-test --file <workflow.wf> --test-name <name> --prompt "<intent>" --data-capture-policy record-later|record-now|model-generated|baseline-replay --definition @.debug/<test-name>-definition.json`. When a ready recorded baseline exists for a model-generated scenario, pass `--base-test-file <ready-test-file>` and include only `testDataOverrides` in the definition. For trigger-context-only variants that reuse the same data path, use `baseline-replay` with `--base-test-file` and no `testDataOverrides`.
6. Refresh an existing matching test with `aistudio do-update-workflow-test --file <workflow.wf> --test-file test/workflows/<lowercase-workflow-code>/<test-name>.json --definition @.debug/<test-name>-definition.json`; preserve valid `testData` unless the scenario needs replacement data or minimal overrides.
7. Run one test with `aistudio run-workflow-test --test-file test/workflows/<lowercase-workflow-code>/<test-name>.json --data-source file|live`. For an ordinary run, omit `--evaluation-mode` and `--judge-provider` so the test uses its configured evaluation mode and the default local judge.
8. Run a workflow suite with `aistudio run-workflow-tests --workflow-code <workflowCode>`. Run an app-scoped suite with `aistudio run-workflow-tests --app-file <app-file>` or `aistudio run-workflow-tests --app-code <appCode>`. Use bare `aistudio run-workflow-tests` only when the user explicitly asks for all workspace tests, full regression, or CI-style validation.

## Direct Suite Execution

File mode controls replay data only; it does not select deterministic evaluation. For an ordinary direct test or suite request, pass the requested `--data-source` and do not pass `--evaluation-mode`. Each test must retain its configured deterministic or hybrid mode. Omit `--judge-provider` to use local judging. Pass `--judge-provider remote` only when the user explicitly requests remote judging. Pass `--evaluation-mode deterministic` only for an explicit deterministic-only request or the transient affected-test validation required during authoring or repair. Never run a deterministic confirmation suite after a configured-mode suite or local judge attachment because it replaces the canonical judged reports with judge-skipped reports.

For a local-judge request spanning multiple app packages, process one package at a time. Run that package's workflow suite once in configured mode, create and attach all pending local workflow judge results, run that package's app suite once in configured mode, and attach all pending local app judge results before moving to the next package. Use the package-scoped reports rebuilt by attachment. Do not begin with an unscoped all-package hybrid run and then rerun each package, and do not run a final deterministic aggregate suite after the package reports are complete.

## Semantic Judge Authoring

For every new sync-plan scenario whose `authoringHints.judgeAuthoringContext.semanticNodes` is non-empty, the model must author `definition.judge`; the CLI does not synthesize the semantic contract. Follow this sequence before `do-generate-workflow-test`:

1. Read the focused sync-plan action's compact `authoringHints.judgeAuthoringContext`. Use its scenario intent, invocation, ordered path, semantic-node roles, terminal contribution, grounding policy, and contract hashes as the factual index.
2. Treat `terminal-output-owner` nodes as the primary semantic contract. A `terminal-output-candidate` is the closest on-path semantic node when explicit output lineage cannot prove ownership. Treat `upstream-semantic` nodes as supporting grounding context only. Do not merge every on-path prompt into one judge contract and do not include semantic nodes listed under `excludedSemanticNodeCodes`.
3. For each terminal owner or candidate, run `aistudio get-workflow-test-judge-context --file <workflow.wf> --scenario-id <scenario-id> --node-code <node-code> --detail full`. The command returns the complete prompt, system prompt, output specifications, dependency path, and downstream transformations without truncation. If a compact field contains a retrieval reference, retrieve it before authoring criteria; never infer omitted content from its hash or length.
4. Write a concise scenario-specific `judge.expectedOutcome` and independent `judge.rubric` items. Every new or changed rubric item must be an object with a stable lowercase kebab-case `id`, a concise business-facing `name`, and its `criterion`. The name must describe what the criterion verifies; never use numbered placeholders such as `Semantic criterion 1` or `Criterion 2`. Judge the final observable output contract, required transformations, and grounding in replayed or recorded evidence. Use upstream semantic prompts only when their output contributes to the terminal result. Do not copy path assertions into the rubric and do not require internal wording that is not part of the final contract.
5. Pass the complete judge object in the scratch definition. The CLI adds compact `judge.authoring` provenance with semantic node codes, terminal owners, scenario ID, and contract hash. Do not hand-author that provenance.

Existing tests are non-migrating. Running, recording, syncing, or refreshing reports must preserve their current judge exactly, including tests with no `judge.authoring` metadata. If the sync plan reports `judgeContractState: "changed"`, explain that review is available but do not update the judge unless the user explicitly asks to review or repair it. For an explicit judge update, retrieve current judge context again and send only the intended judge changes through `do-update-workflow-test`; the CLI then records fresh provenance.

## LOOP Replay Coverage

LOOP coverage is an additional scenario facet. Preserve the sync plan's existing `scenario.kind`, `scenario.appStage`, and invocation input. Read `scenario.coverage.loopReplay` and `authoringHints.loopReplayGuidance`; never replace an app-stage or primary-path identity with a LOOP-specific scenario kind.

For `boundary-output`, use the focused sync-plan action's `dataCapturePolicy` and `baseTestFile` exactly. `record-now` records the representative scenario. When compatible app stages share the same data path and LOOP boundary contract, prefer `InitDisplay` as that representative and use `baseline-replay` for the others. A `baseline-replay` action must reuse its `baseTestFile` testData and LOOP evidence exactly; never record that stage live. `model-generated` supplies complete boundary replay data without live recording. `record-later` remains pending until its boundary output is recorded. File replay overrides every outermost LOOP listed by the scenario and intentionally skips each overridden body, including nested LOOPs inside that body. Keep the sync plan boundary path assertions: they include the outer LOOP boundaries and downstream consumers, and classify every descendant of an overridden boundary under `mustNotExecute`. During live recording only, the CLI removes those descendants from breakpoints so the real LOOP body can execute and be captured. Do not repair the persisted replay path from the full live recording path.

For `single-iteration`, read the boundary test named by `authoringHints.loopReplayGuidance.evidenceTestFile` only as a read-only synthesis source. `evidenceUsage` is `read-only-synthesis-source` and `useAsBaseTestFile` is `false`; never pass that file through `--base-test-file`. Start from `authoringHints.loopReplayGuidance.testDataTemplate`. Treat each entry in `authoringHints.loopReplayGuidance.consistencyGroups` as one atomic synthesis decision: selected LOOP items, generated descendant responses, nested parent-child items, and related top-level LOOPs in that group must describe one coherent execution. Prefer a representative item already present in the compact live evidence when it can exercise the scenario. When the recorded samples do not cover `targetBranch`, synthesize the smallest coherent variation that satisfies `routingDecisionContext` while preserving the recorded schema, identifiers, and parent-child relationships. For every LOOP listed in `authoringHints.loopReplayGuidance.topology`, replace its `selectedItem: null` with that selected or synthesized item and preserve `selectedItemSource: "model-generated"`. For nested LOOPs, synthesize a coherent outer-to-inner chain: the child item must belong to the selected parent and every ancestor LOOP must have exactly one selected item. A LOOP listed in `dataGuidance.zeroIterationLoops` is intentionally empty and must not receive a selected item or generated descendant data. Add observed `sourceCollectionSize` values when the evidence provides them. Generate complete node entries for `dataGuidance.requiredGeneratedNodeCodes`. Replace every required generated node's placeholder `input` and `response`, including BO_FUNCTION, EXTERNAL_REST, WORKFLOW, FUNCTION, LLM, or AGENT descendants listed by the action. Use `testDataOverrides` only for `dataGuidance.overrideRequiredNodeCodes`. The CLI clones each complete current LOOP node, replaces only its `collection` input with the corresponding one-item collection, applies flat recordable-node output overrides, and runs CODE, CONDITION, SWITCH, LLM, and AGENT descendants normally. Never edit the workflow file to create one-item collections.

Scenario discovery covers nested FOR LOOPs, multiple top-level FOR LOOPs on the same execution route, LOOP iteration modes `SEQUENTIAL` and `PARALLEL`, and LOOPs in separate branches of a PARALLEL control-flow node when the branch convergence point is explicit or can be resolved safely. Keep required app-stage, REST, and chat scenarios unchanged. For LOOP bodies without distinct inner CONDITION or SWITCH routes, add one dedicated internals test per traversed LOOP topology. When the sync plan exposes unique branch paths inside a LOOP, author one evidence-backed single-iteration test per unique execution path, preserve the existing branch scenario kind and app-stage contract, and do not create an additional generic internals test for an identical route. Never expand LOOP paths into a Cartesian product of app stages and branch outcomes. When `parallelBranchGroups` is present, synthesize each branch independently. Preserve nested parent-child relationships within a branch, but do not invent cross-branch data relationships, execution ordering, or concurrency assertions. File replay still depends on the runtime debug API propagating overridden branch-node outputs through PARALLEL convergence. If the same asserted path passes live but file replay loses an overridden BO, CODE consumer, LLM consumer, or LOOP output after convergence, classify it as a runtime replay-binding failure; do not modify the workflow, test input, or path assertions to compensate. Do not invent iteration-scope override fields. WHILE containers execute their real condition and body normally. For every recordable descendant on the asserted body-entering path, use ordinary `testData.nodes`; the runtime reuses that one representative fixture whenever the node executes across WHILE iterations. LLM, AGENT, CODE, CONDITION, and SWITCH descendants continue executing normally. Preserve the existing scenario kind and app-stage contract, and do not create `loopReplay`, boundary-output, selected-item, iteration-count, or WHILE spec-override metadata. Distinct per-iteration override values, order or concurrency assertions, and PARALLEL routes whose convergence cannot be resolved safely remain unsupported; report the exact topology instead of guessing.

## Sync Execution Contract

Mode selection matters. If the user asks to show, inspect, preview, display, or get the workflow test sync plan, run `get-workflow-test-sync-plan --file <workflow.wf>` and stop after explaining that read-only plan. Do not generate, update, record, run, or judge tests for a preview request. If the user asks to run, execute, generate, regenerate, sync, create or update tests, or complete the workflow test sync plan, treat it as execution mode. In execution mode, a plan with `finalSummaryAllowed: false` or a non-empty `coverageExecution.nextActionIds` requires the next tool call; pending counts are not a valid interim or final response.

Process one workflow at a time. Within that workflow, `coverageExecution.nextActionIds` and `coverageExecution.nextActions` contain the single next action to execute for ordinary coverage. Do not infer additional executable actions from other rows in the full text table. Issue at most one mutating generate, update, record, apply, or save command at a time; never start a second command for the same test or workflow artifact while the first is running. An action is complete when the CLI has materialized the source test, completed its required recording, compaction, baseline application, or model-generated data, and deterministically validated that affected test, or when a concrete attempted scenario-level deferral is accounted for. Immediately refresh the focused sync plan after that action and execute the next returned action without asking. After ordinary actions are complete, if `conversationCoverage.status` is `model-authoring-required`, read `conversationCoverage.contextCommand`, follow `workflow-conversation-test-authoring.md`, author and validate the missing HUMAN/WAIT conversation interactions, then refresh the plan. Do not run a full workflow suite, run hybrid evaluation, or attach local judge results while create or update actions remain. The same restriction applies while required conversation coverage remains.

A scratch definition under `.debug/` is temporary authoring input, not a generated test or stopping point. For a create or update action, immediately run `do-generate-workflow-test` or `do-update-workflow-test`, then verify the source-controlled `test/workflows/.../<test-name>.json` exists. Before generation, if the focused action's `authoringHints.judgeAuthoringContext.semanticNodes` is non-empty, complete the Semantic Judge Authoring sequence above and include `definition.judge`; do not wait for the generate command to reject an incomplete semantic definition. A test file is not ready merely because it exists. For `record-now`, attempt live recording. For `model-generated`, embed complete generated data. For `baseline-replay`, require a ready base test. Run that affected test with file data and deterministic evaluation before refreshing the plan. Do not report an action as complete until its required data work and deterministic validation are accounted for.

Treat `needs-model-test-data` as part of the same scaffold action. Read the emitted version 2 workflow-backed request and copy `replayDataPayloadTemplate` exactly. Fill every mutable artifact named by `consistencyGroups`; do not add or remove node or LOOP codes. Compact or synthesize every artifact in a group together so source collections, LOOP boundaries, selected items, identifiers, counts, and parent-child relationships stay coherent. The CLI merges that payload into `testDataTemplate` and preserves `rawArtifactsToPreserve`. Apply it with `do-apply-workflow-test-data` for workflow tests or `do-apply-app-test-data` for app tests, then verify ready data before validating the affected test and refreshing the focused plan. `nodesNeedingModelData` remains compatibility context for ordinary node-only requests, not the complete mutable-artifact contract. Treat `needs-judge` as a continuation only for an explicit single-test hybrid request or the final configured-mode workflow suite. Ordinary scaffold actions do not run hybrid evaluation and therefore do not create per-action judge continuations.

The latest focused workflow sync plan is the sole authority for generation completion. After each action is validated or deferred, rerun `get-workflow-test-sync-plan --recommended-batch-only true --format focused-json` and execute its next action without asking for confirmation. The workflow generation loop is complete only when the latest plan reports `finalSummaryAllowed: true`, no create or update action remains, and any reported `conversationCoverage` is `covered` or explicitly `unsupported`. This means all supported actions are accounted for, not that every generated test passed. Semantic failures and scenario-level deferred outcomes remain reportable results and do not stop unrelated actions.

An execution-mode sync request has only three user-facing stopping conditions: the latest plan allows the final summary with no create or update action remaining; a concrete command, authentication, missing-file, or required-input failure prevents the next action; or the user explicitly asks to stop. Passing or failing one test, completing one phase, having other tests still pending, substantial elapsed time, an estimate that little execution time or context remains, or useful partial progress are not stopping conditions. Keep any host-required progress update concise and continue with the next tool call; never turn a progress update into a partial handoff.

For an app with multiple required backing workflows, process workflows sequentially in the app plan's order. Never request plans, generate tests, record data, run tests, or judge results for two backing workflows concurrently. Stay with the current workflow until its latest plan satisfies the generation completion condition above, then run that workflow's final canonical configured-mode suite exactly once without `--run-label` and complete its canonical judge attachment once without `--run-label` before moving to the next workflow. Use the suite report rebuilt by attachment directly. If an unrecoverable primary blocker makes further actions for that workflow impossible, account for that workflow with the exact failed scenario and reason, then continue the next independent backing workflow. A failing generated test does not justify switching early or rerunning the full suite. Stop the execution request only when the user asks to stop or a workflow-wide hard failure such as authentication, a missing required file or input, or an unrecoverable command error prevents any further work.

The sync plan may include input-aware path metadata. Use it to decide what needs live proof before a scenario-backed test is trusted:

- `pathSource: "predicted"` means the path came from topology only. It is advisory, not final proof. If live execution contradicts it, refine the scratch definition's `pathAssertions` from the observed runtime path instead of forcing the topology guess.
- `pathSource: "input-derived"` means the path was derived from trigger input, run profile input, or condition/switch expression analysis. Treat it as a high-confidence candidate. If `requiresRuntimePathValidation` is true, run or record with the exact sync-plan `suggestedInput` before treating the path as proven. If live execution contradicts it, report an input/routing mismatch with the observed path and the relevant `inputDependencies`; do not silently rewrite it as if the candidate had been proven.
- `pathSource: "observed"` means a previous live execution path binding is current for the same normalized input and workflow definition. You may use it as authoritative.
- `pathSource: "user-specified"` means the user described the path or routing intent. Treat it as a candidate until live execution proves it. If the observed path matches, write the scenario-backed test with the observed path. If it does not match, report the divergence, offer a custom test if the user still wants that assertion, and do not persist an incorrect scenario-backed path.

When an action includes `inputDependencies`, read them before authoring input or path assertions. They explain which runtime parameter and value the workflow branch depends on, such as `parameters.prjPjfRoutingContext = "redwoodui"`. Preserve the sync-plan `suggestedInput` exactly for these scenarios unless the user explicitly provides a different runtime input. Exception: when `inputGuidance.useSuggestedInput` is `false` for an advisory primary chat input, interpret the current action's `routingDecisionContext` and provide an explicit model-synthesized `definition.input` instead of preserving the fallback. An advisory primary input is not an independent invocation contract: never convert it into an app trigger when the same normalized route, terminal behavior, and LOOP coverage already belong to an app-stage action. If the CLI rejects that duplicate, refresh the sync plan and use the app-stage action; create equivalent custom coverage only when the user explicitly requests it. For Query app-stage scenarios, preserve the trigger envelope fields but synthesize `input.message` per the Query message precedence below; do not treat the CLI's default empty message as intentional. Do not replace REST parameters with empty schema defaults. If the user asks to use a run profile, that user instruction takes precedence over inferred values. For REST-trigger and input-dependent secondary scenarios, inspect the supported REST trigger input parameters, matching run profiles, `inputDependencies`, and the `CONDITION` or `SWITCH` expressions on the intended scenario path before writing `input.parameters`. Populate the specific parameters that route the workflow to that scenario; do not rely on a generic message-only input when the branch depends on REST parameters, active conversation state, chat history, attachment context, or other runtime fields. If the required runtime context cannot be inferred from the sync plan, run profile, workflow purpose, or user prompt, classify that scenario as blocked input context or ask for the missing value instead of generating a misleading test.

InvokeAction is the only app stage with sync-plan input variants. The default sync plan requires one representative InvokeAction test and does not queue every run-profile payload. `invokeActionCoverage` reports the existing representative coverage and any optional variants. Generate optional variants only when the user explicitly asks for additional, all, exhaustive, or run-profile-specific InvokeAction coverage; rerun the plan with `--include-optional-invoke-action-variants true` and preserve that option on every focused rerun until the requested variants are accounted for. Do not apply this expansion to InitDisplay, Query, Summary, or other app stages.

For an existing InvokeAction test, the persisted `input` and its current live-observed path binding are authoritative. A changed active run profile is an authoring suggestion for new coverage, not drift that permits overwriting the existing test. If the user changes an InvokeAction input, update the test through `do-update-workflow-test`, run or record that exact input, and keep the observed execution path when validation succeeds. Do not restore the old run-profile payload on the next sync. Identify InvokeAction coverage from `scenario.appStage` and `scenario.coverageRole`, with runtime input used only for legacy metadata compatibility; never infer it from the file name or `testName`.

Apply the same persisted-input authority to an existing Query app-stage test when its app-stage trigger envelope is unchanged and its current path binding still matches the workflow definition. Preserve the meaningful persisted Query message even if a refreshed run profile or sync suggestion contains a different or empty message. A new suggested message is input for new coverage, not drift that permits replacing a validated Query question.

When the user asks to remove a workflow test, use `do-delete-workflow-test --test-file <path>` so the CLI removes the source test, removes its individual report, and refreshes parent reports. Deleting an optional InvokeAction variant does not make normal sync recreate it. Deleting a representative InvokeAction test also does not recreate that exact variant when another valid InvokeAction test still satisfies the minimum coverage. If no InvokeAction test remains, normal sync proposes one representative test.

When the sync plan marks scenarios with `primaryClass: true` and `requiresRuntimePathValidation: true`, complete those primary-class live validations first. Do not generate a large set of secondary branch, data, or edge-case tests while every primary-class route remains unproven. If the sync plan says secondary scenarios were suppressed by primary validation gating, generate or record at least one valid primary-class scenario, rerun the sync plan, then continue with the remaining actions.

When primary coverage is pending, start with the compact `get-workflow-test-sync-plan --file <workflow-file>` text output and its action table. If the primary action's `inputGuidance.useSuggestedInput` is `false` and `routingDecisionContext` is present, retrieve the focused JSON view before generating that action and synthesize a natural scenario-specific `definition.input` from the current action's raw routing expressions and expected outcomes. Treat the workflow-derived `suggestedInput` as advisory in this case, but do not repurpose the primary scenario as an app-stage invocation already represented by another sync-plan action. Preserve exact user, run-profile, REST, app-stage, or expression-derived input without model substitution.

For scenario-backed actions, `scenario.id` is the stable sync identity; `testName` and the physical filename are user-facing labels. Preserve the current action's persisted `testName` and `testFile` for an existing test. Never rename an existing test merely because a refreshed plan recommends a different default name, and never infer scenario behavior from either label. Use the sync-plan `purpose` as the initial `scenario.intent`; do not reinterpret the target data state or branch in model-authored wording. Omit `pathAssertions` from the definition when the focused plan omits `expectedPath`; the CLI rehydrates the complete path from scenario identity. Copy `expectedPath` only when the full plan explicitly provides it, and then copy both `mustExecute` and `mustNotExecute` exactly. Never hand-author a partial alternative.

Primary coverage is ordered by the focused sync plan. Execute the listed `primary-recording` action first, complete live recording and deterministic validation, then refresh the focused plan. Execute a listed `primary-replay` action only when that refreshed plan provides a ready `baseTestFile`; validate the affected replay test deterministically and refresh again. Recording, required-data, deterministic, path, or baseline failures are structural and may prevent dependent coverage. Semantic judging belongs to the final configured-mode suite, not the create or update loop. Do not call the final-summary command while primary or other create or update actions remain.

After primary structural validation is established, run the focused sync plan and execute its single listed `secondary` action. Use that action's `costClass`, `lowRisk`, and `authoringHints` to understand path complexity, target branch, input construction, data reuse, and validation boundaries. Validate the affected test deterministically, then refresh the focused plan for the next action. Do not infer cost or intent from full path arrays or infer additional executable actions from the full text table.

For `record-now` branch-path and switch-value actions, use `authoringHints.dataGuidance.branchForcingHints` to construct live input, not synthetic test data. Do not carry active-request, pending-decision, prior classification, or other accumulated state from another scenario unless the hints require it. Treat `deep-semantic` paths as semantic routes and author focused scenario input and data for the named target branch.

If the first attempt misses the intended branch, make one materially different input or test-data attempt. A branch is missed only when `result.run.nodeResults` does not contain both the target decision node and the expected branch successor identified by the action's validation guidance. If both nodes executed and the path diverged later, branch forcing succeeded: retain the generated failing test, report the first downstream divergence, continue the sync loop, and do not retry the input or mark the scenario unable to generate. For an actual branch miss, change the message, trigger parameters, run-profile fields, active context, or branch-forcing data; rerunning the same input with the same test data does not count. For model-generated data, record the changed strategy and affected node codes in the second attempt. For a secondary `record-now` action that reaches the intended branch, use the observed `result.run.nodeResults` path and filter the sync-plan `mustNotExecute` accordingly. The CLI rejects a path-divergence deferral with fewer than two materially different attempts. After two actual branch misses, call `mark-workflow-test-unable-to-generate` with both attempted inputs, test-data strategies when applicable, and observed versus expected branches. This defers only that scenario and its direct dependents, not the workflow.

A secondary semantic judge failure from the final configured-mode suite is a completed generated failure and does not invalidate other scenarios. A secondary deterministic or path failure may defer that scenario and direct dependents after the required second attempt, while unrelated actions continue. Attempt supported live recording without a separate user decision merely because a path includes mutating or write-like nodes; report those effects in the final summary. Never expose internal cost units or hidden scheduling math. Validate each affected test deterministically, refresh the focused sync plan, and continue until each supported action is complete, generated and failing, or deferred.

## Sync State Interpretation

Interpret sync-loop state mechanically. `actions-remaining` means execute the single action in `coverageExecution.nextActionIds`, validate the affected test deterministically, then immediately refresh the focused plan and execute the next returned action. `deferred-only` with `finalSummaryAllowed: false` means refresh the focused plan for any remaining action. `deferred-only` or `ready-for-final-summary` with `finalSummaryAllowed: true` means generation is accounted and final validation may begin. `summary.deferred` is cumulative reporting data, not a reason to stop or ignore remaining actions. A semantic judge failure is also a definitive generated result, not a hard command failure.

During an active execution loop, do not output progress narration between tool calls, call command discovery, search for a batch executor, or substitute a summary for the next action. The only user-facing response is the final response after generation is accounted, final validation is complete, and `get-workflow-test-final-summary` has been called.

Use the normal text plan to begin or explain the workflow inventory. During execution, use `get-workflow-test-sync-plan --recommended-batch-only true --format focused-json` after each action so the next action, model input synthesis context, and judge authoring context remain focused without repeating the full inventory. Use the full text or JSON plan only when the focused result lacks information required to diagnose a concrete failure. Do not reread completed test files or reports after every action; read persisted artifacts only when the authoring checklist, deterministic validation, judge authoring, repair, or failure diagnosis requires them. In an app flow, finish the current workflow's supported actions, reach `finalSummaryAllowed: true`, and complete its final suite and judge attachment before checking the next required workflow. Do not interleave workflow sync commands.

After the latest sync plan reports `finalSummaryAllowed: true` and the final suite plus any judge attachment are complete, call `get-workflow-test-final-summary --file <workflow-file>` exactly once. Compose the final response with the workflow creation, change, test-generation, or run outcome first, followed by a section named exactly `Validation and Insights`. Preserve the command's test counts, workflow suite `Report:` link, `Metrics:`, and `Optimization:`. Preserve its compact issue count and natural-language next step when failures, pending judges, or unable-to-generate scenarios exist. Do not list every failing or deferred test in the default final response. Use `--format json` only when the user asks for detailed failure diagnostics or structured output. A generated test failure or unable-to-generate scenario does not stop unrelated sync actions; complete the sync loop before producing this final response.

If a concrete primary blocker prevents suite creation and no valid final-summary artifact exists, do not omit the outcome or fabricate report data. Use the latest sync plan and recording attempt to report the failed primary scenario, observed fallback or command failure, dependent pending tests, and one natural-language corrective action. Preserve valid suite links, metrics, and optimization information from any independent workflow that did complete.

Before classifying a live recording that reached an unexpected fallback branch as an environment data blocker, follow this order: verify that every explicitly requested Business Object and function was selected exactly; verify BO input bindings and downstream fields against that function's metadata and effective output specification; inspect guard expressions; inspect trigger/input shape; inspect generated or recorded `testData` preconditions; then inspect the actual live response shape. A fallback node label describes what branch executed; it does not prove that live data is missing until workflow authoring, routing logic, input shape, and response fields are verified. If an authoring defect is found, repair the workflow, validate it, save or normalize the changed DRAFT once, refresh the sync plan, and retry the primary recording once. Only after those checks pass may a genuinely missing live value be reported as an environment-data blocker.

For condition, switch, code, return, or other expression-bearing node edits, write the inputs patch to a scratch JSON file and pass it with `--inputs-patch @.debug/<name>-inputs.json`. Do not pass inline JSON containing empty-string literals, quotes, `$context`, `{{...}}`, comparison operators, or expression syntax through shell command arguments. Prefer quote-free existence checks for guard conditions when equivalent. After modifying condition guards, run workflow validation or read the workflow back before recording or running tests. If validation passes but runtime routes to an unexpected fallback, read the workflow file directly when the condition node code is known, or use `aistudio get-workflow-test-context --file <workflow.wf>` to inspect condition node inputs and current path assertions. Look for expressions that end with a comparison operator and no right-hand operand, that contain stripped empty-string literals, or that compare against an absent literal, before reporting missing environment data.

When running workflow tests, scope the run to the artifact the user asked about. For one workflow, pass `--workflow-code <workflowCode>`. For one app, pass `--app-file <app-file>` or `--app-code <appCode>` so only that app's active and additional workflow-agent tests run. Do not use bare `run-workflow-tests` for a workflow-specific or app-specific request, because it runs every workflow test in the workspace and can fail on unrelated artifacts.

When the user asks to compare, switch, try, benchmark, or evaluate workflow quality with a different LLM/model, do not edit workflow files or workflow test JSON. First inspect supported choices with `aistudio list-workflow-model-configurations` or `aistudio get-workflow-model-configuration --code <modelConfigurationCode>`, then inspect eligible workflow nodes with `aistudio get-workflow-model-override-targets --file <workflow.wf> --include-ineligible true`. For one-test comparison, still use `run-workflow-tests --workflow-code <workflowCode> --test-name <testName>` so a labeled suite report exists for `compare-workflow-test-runs`; do not use `run-workflow-test` alone when a comparison report will be generated.

For fair model quality comparison, prefer recorded `--data-source file` runs when test data is already ready, because each model sees the same replayed BO/REST/tool/vector/deeplink data. Use `--data-source live` only when the user explicitly wants live environment behavior or recorded data does not exist. For semantic outputs from `LLM`, `AGENT`, `MULTI_AGENT`, or LLM-backed `DOCUMENT_PROCESSOR`, compare the final output preview, deterministic routing checks, and judge result/rubric. Do not add deterministic final-output assertions merely because a model comparison was requested. With the default `local` judge provider, do not stop while any selected baseline or candidate case is `needs-judge`: read the run-labeled `.debug/workflow-test-runs/<safe-run-label>/<test-name>-judge-request.json` request, write the matching judge result in that same run-label directory, attach it with `aistudio attach-workflow-test-judge-results --workflow-code <workflowCode> --run-label <label> --cleanup-scratch true`, and continue only after the selected run-labeled suite has 0 failed and 0 needs judge. The embedded `workflow.workflowCode` remains the real uppercase workflow code. Create a new test when the user needs a different dataset.

For sync-plan generated tests, run the changed input live and retain it only with a current observed path binding; changing the context invalidates that binding and requires another live validation. Do not invent credentials, access tokens, or sensitive production identifiers. Use explicit user values or clearly synthetic non-secret values.

For app-stage tests, do not confuse a valid trigger envelope with a complete scenario input. Preserve the legal app or REST trigger shape from the sync plan, then supply stage-appropriate semantic input when the stage requires it. Additionally, `judge.expectedOutcome` for a Query test must describe what a high-quality answer to the synthesized question should contain. Do not copy LLM node prompt sections (`DATA:`, `TASK:`, `OUTPUT:`) or unexpanded `{{$context...}}` expressions into `expectedOutcome`. `InvokeAction` usually requires action identity and minimal action payload/context. `FillParameters` usually requires missing-parameter context for the relevant action. `AdditionalContent` usually requires panel, card, or content context. `InitCommunications` and `SendCommunication` usually require communication context, and mutating send paths remain subject to the existing capture policy. Infer this semantic input from the app, workflow intent, existing ready baseline, or user prompt. If required non-Query app context cannot be inferred safely, do not generate an empty shell test. Report the scenario as blocked input context with the missing context and the exact next step needed from the user, or ask for explicit approval to use model-generated synthetic context.

Before generating a primary-path `record-now` test, check whether the workflow trigger declares named inputs required to exercise that primary path. A required trigger input is unresolved when the workflow trigger declares it, the primary path consumes it in a BO_FUNCTION, CONDITION, or other executable node on that path, and no concrete value exists in the user's original workflow prompt or an existing source-controlled test for this same workflow. Existing tests from other workflows, neighboring workspaces, session memory, CLI examples, help text, BO samples, and plausible values visible in conversation are not valid sources. Treat an unresolved required trigger input like a missing secret or missing environment data: do not infer, guess, reuse, or synthesize a value for primary-path live recording.

If a primary-path `record-now` scenario has unresolved required trigger inputs, stop that scenario and surface a `needs-user-input` action instead of running `do-generate-workflow-test` for it. Name the workflow and blocked scenario, list each missing parameter by name and type when known, and state the exact value needed for live recording. The REST trigger declares required input personId (string) with no default in the prompt or existing tests. Provide a valid personId value to proceed with record-now data capture for the primary path.` Make clear that only the `record-now` primary-path recording is blocked.

You may create `model-generated` tests with synthetic or sentinel trigger parameters and `testDataOverrides` only for a CONDITION or SWITCH outcome, early return, or other distinct executable route that the sync plan discovered. You may also create `baseline-replay` tests after a real baseline exists. Never invent a generic empty-data test merely because a recordable node returns a collection. Empty or missing data warrants an automatic test only when the workflow has a distinct routed outcome for that state. Never promote an empty-data or sentinel-parameter case to the primary path, and do not use a synthetic value such as `NO_ASSIGNMENT_PERSON` as the representative `record-now` input.

When the user later supplies the missing trigger value, resume only the blocked primary-path `record-now` scenario using that exact value. Do not modify alternate-path tests that were already created unless the user asks or the workflow changed.

Treat those fields as authoritative. ### Terminal Node Output Classification

Before writing output assertions for a test scenario, identify the terminal node — the last node in `pathAssertions.mustExecute` — and apply the matching strategy.

**Class A: semantic-output terminal node**

- Set `defaults.evaluationMode` to `"hybrid"`.
- Do NOT add auto-generated deterministic final-output assertions: `assertions.equals`, `assertions.contains`, `assertions.startsWith`, `assertions.endsWith`, or `assertions.notContains`.
- Semantic-output nodes include `LLM`, `AGENT`, `MULTI_AGENT`, `WORKFLOW`, `RAG_DOCUMENT_TOOL`, and `DOCUMENT_PROCESSOR` when `extractWithLlm` is true. A `RETURN` expression that references output from one of these nodes is also treated as semantic-output.
- Semantic output may be generated, retrieval-answer-like, delegated to another workflow, or otherwise wording-sensitive. Even with replayed file data, it may paraphrase, reformat, or vary its output between runs.
- Prove routing using `pathAssertions.mustExecute` and `pathAssertions.mustNotExecute`.
- Prove output quality using the local judge rubric. Always include the criterion: `"The output is grounded in the replayed test data."`
- Do not act on `assertionSuggestions` from the test runner as literal assertions for these tests. Those suggestions describe what appeared in one run; they are not stable across runs.
- `WORKFLOW` nodes are recordable parent workflow boundaries. Parent tests record and replay the child workflow node output, assert parent routing/final-output behavior, and do not assert child workflow internals. Direct regression coverage for the child workflow belongs in that child workflow's own tests.

**Class B: RETURN node with a hardcoded literal value (no `{{...}}` in returnValue)**

- Set `defaults.evaluationMode` to `"deterministic"`.
- Add `assertions.equals` set to the exact literal string from the node's `returnValue` input.
- Do NOT write a `judge` block — the output is provably exact and the judge will be skipped anyway in deterministic mode.

**Class C: RETURN node with an expression returnValue (contains `{{...}}`)**

- Set `defaults.evaluationMode` to `"deterministic"`.
- Add `assertions.equals` only when the expression value is predictable from the test input. For example: `returnValue = "{{$context.$triggers.REST.$input.my_string}}"` and the test input has `my_string: "abc"` -> `assertions.equals: "abc"` is stable.
- If the expression depends on upstream LLM output or runtime context, leave `assertions` empty.
- Do NOT write a `judge` block.

**Auto-generation default only.** The rule "do not add output assertions to a Class A test" applies to auto-generated assertions during `do-generate-workflow-test`. A user may manually add any assertion type — `equals`, `contains`, `startsWith`, `notContains` — to a Class A test when they know the output characteristic is stable for that specific workflow and prompt. This is a deliberate user choice and must be accommodated without restriction or warning. Manually-added assertions are respected by the runner and must not be stripped by automated update flows.

**Do not auto-repair failing assertions. Do not change the workflow.** If any assertion on a test fails — regardless of assertion type or terminal node class — the model must not do any of the following without explicit user instruction:
- Update or remove the failing assertion to match the observed output.
- Change any workflow node (prompt text, node inputs, edges, conditions, return values) to make the assertion pass.
- Change any LLM node's system prompt or user prompt.
- Remove or add workflow nodes.

When a user-placed assertion fails, report the test name, failed assertion, and final output preview, then stop. Wait for the user to decide whether the assertion, the workflow, or the test data needs to change. Do not suggest a replacement assertion value in the user-facing summary.

Do not add a judge to a Class B or C test; if the JSON schema requires the `judge` field, keep only the inert CLI-generated stub and remember it is skipped in deterministic mode.

The sync plan already provides scenario descriptions, create/update/review actions, and ready baseline test file pointers when available. If that output is sufficient to write the scratch definition, skip `get-workflow-test-context` entirely. Do not call context immediately after sync plan just to inspect the workflow.

After any successful workflow create or material workflow edit, automatically sync tests. This applies to node additions, node edits, edge changes, node deletion, prompt/code changes, metadata changes that alter intent, and direct workflow-file repairs when the CLI did not support the operation. Run `get-workflow-test-sync-plan` to identify create, update, and review actions across the primary path, branch or switch outcomes, early returns, and other distinct reachable execution routes. Execute create/update actions without waiting for scenario confirmation. Do not invent data variations that do not map to a distinct workflow route or invocation contract. Respect explicit user opt-out, and ask only for external blockers such as remote overwrite conflicts, missing required environment data, or secrets. Do not delete `review` tests automatically; report that they appear custom or stale.

For sync-plan `update` actions, do not blindly refresh every listed test. Inspect the existing test first and update only when the workflow change creates a concrete mismatch in scenario intent, path assertions, data requirements, deterministic assertions, judge metadata, or expected static output. If the existing test already matches the intended definition, report it as already current and skip the update command.

If the first sync plan has model-generated alternate-path actions but no `baseTestFile` because no primary-path baseline exists yet, create/record/run the representative `record-now` baseline first. Do not rerun `get-workflow-test-sync-plan` when the previous sync plan already identified the alternate create/update actions and the primary baseline path is now known; proceed directly to create or update alternate tests with `--base-test-file <primary-test-file>`. Rerun sync plan only if workflow topology changed, baseline generation failed, the baseline path is unknown, or the previous sync plan did not include baseline-dependent alternate actions. Do not work around CLI validation by manually cloning a final `test/workflows/...` JSON file. If `model-generated` reports that `--definition` is required or that a baseline should be used, correct the scratch definition and rerun the CLI command.

Before creating or updating tests, collapse overlapping scenarios: if a representative primary or app-stage path already proves the same execution route, downstream behavior, terminal contract, and LOOP replay mode, do not also create a generic primary or branch-only duplicate. Keep scenarios separate when they use a different invocation contract, app stage, REST trigger, reachable branch, terminal behavior, or LOOP mode. Distinct empty-data outcomes remain separate only when the workflow explicitly routes those dependencies to different paths. Do not collapse explicitly requested distinct trigger values: include trigger type and trigger parameters in duplicate checks, and keep separate REST-trigger tests for values such as "with llm" and "without llm" when both values are meaningful even if they execute the same broad path. Scenario order should follow workflow topology: primary path first, trigger variations that reuse the primary path, authored branch or switch outcomes next in graph order, custom and review tests last. When deciding data-capture policy, use this lifecycle: `record-now` records real data once and then runs from file, `record-later` creates now and records before file runs, `model-generated` means the workflow has no recordable nodes, the local assistant supplies complete `testData`, or the local assistant supplies a small set of baseline overrides for a discovered route, and `baseline-replay` reuses an existing ready baseline while changing only runtime `input`.

Workflow tests can be generated for any workflow, including control-flow-only workflows, static-return workflows, CODE-only workflows, and BO/REST/tool workflows without LLM nodes. `testData.nodes` may be `{}` when the workflow has no recordable external-data nodes. For `--data-capture-policy model-generated` tests with no recordable nodes, omit `testData` from the scratch definition; the CLI will create ready empty `testData.nodes = {}` with `capturePolicy = "model-generated"`. Do not hand-author partial empty `testData` like `{ "nodes": {} }`. Use deterministic evaluation for workflows whose final output is fully covered by static/path assertions or does not require semantic-output judging. Use hybrid evaluation when final output depends on a semantic-output node: `LLM`, `AGENT`, `MULTI_AGENT`, `WORKFLOW`, `RAG_DOCUMENT_TOOL`, or `DOCUMENT_PROCESSOR` with `extractWithLlm = true`.

Run the self-healing loop in three phases: Scaffold, Observe, Validate. Do not attach judge results until deterministic mode is clean.

Phase 1 - Scaffold: generate or update tests from the sync plan. For static terminal `RETURN` scenarios, use `assertions.equals` when the return value is a known literal. For scenarios whose final answer depends on semantic-output nodes, include `pathAssertions`, a complete `judge` block with hand-authored `judge.expectedOutcome` and `judge.rubric`, but do not add guessed deterministic output assertions from `testData`, workflow descriptions, node prompts, BO/tool metadata, expected semantic concepts, or implementation-safety wording.

Immediately after every `do-generate-workflow-test` call, before `do-apply-workflow-test-data --cleanup-scratch true` or any other operation that may delete `.debug/`, read the generated test file and inspect `input`, `judge.expectedOutcome`, `judge.rubric`, `defaults.evaluationMode`, terminal-node strategy, deterministic assertions, and path assertions. Repair with `aistudio do-update-workflow-test --file <workflow-file> --test-file <test-file> --definition @.debug/<test-name>-definition.json` only when the persisted file fails this checklist: the intended runtime invocation shape from explicit definition, sync-plan `suggestedInput`, or active run profile is preserved; semantic-output terminal tests use `hybrid`, have no auto-generated output assertions, and have substantive judge metadata; literal RETURN terminal tests use deterministic `assertions.equals`; stable trigger-input RETURN expressions use deterministic `assertions.equals` only when the exact value comes from fixed `input.parameters`; `judge.expectedOutcome` is plain human-readable text with no unexpanded `{{$context...}}` expressions, no raw prompt sections such as `DATA:`, `TASK:`, `OUTPUT:`, or `Required content:`, and no auto-generated prefix `"The final answer satisfies the workflow output contract:"`. Query app-stage tests have an additional checkpoint: if `input.parameters.appHint`, `input.parameters.appStage`, or `input.parameters.OraMessageHint` is `Query` and `input.message` is empty, verify the test purpose, `authoring.userPrompt`, or scratch definition explicitly says `limited empty-message Query smoke coverage`. If it does not, repair the test before running it by preserving the app trigger envelope and adding a concrete user-facing Query message from the user prompt, app purpose, workflow purpose, or scenario purpose. Live-recorded branch-path and switch-value tests use the observed-path model. After `do-record-workflow-test` completes, run the generated test with `--data-source file --evaluation-mode deterministic`. If path assertions pass, the intended branch was taken: derive updated path assertions from the run report at `test-reports/workflows/<workflow-code>/<test-name>/result.json`. Use `result.run.nodeResults` keys as the observed mustExecute. Preserve the sync-plan scenario's mustNotExecute, removing only node codes that appear in the observed mustExecute. If the observed path differs from the sync-plan prediction, update the test with `do-update-workflow-test` using the corrected pathAssertions. Do not force the sync-plan predicted path when live execution proves otherwise. If path assertions fail, the live run took a different branch than intended. Do not accept the wrong branch as a valid test. Retry using `do-update-workflow-test` with a different input that more directly forces the target branch via branchForcingHints. Track attempts per scenario ID in this session. After 2 total failed attempts: write `.debug/<test-name>-unable-to-generate.json` and call `aistudio mark-workflow-test-unable-to-generate --file <wf> --blocker @.debug/<test-name>-unable-to-generate.json` (see blocker sidecar below). Immediately rerun `get-workflow-test-sync-plan --recommended-batch-only true --format focused-json` and execute the next action in `nextActionIds` without producing any user-facing text. The deferred scenario will appear automatically under Unable to generate in the final summary — do not surface it as an interim message during the sync loop. The `mark-workflow-test-unable-to-generate` command automatically deletes the test file from `test/workflows/` so the scenario appears in Unable to generate in the final summary, not Generated and failing. If all checks pass, skip `do-update-workflow-test` entirely and proceed. Do not run a blanket `do-update-workflow-test` refresh pass merely because a later sync plan marks existing tests as refreshable. Use `do-update-workflow-test` only for a concrete delta: fixing bad or missing judge metadata, clearing invalid deterministic assertions, correcting path assertions, preserving explicit user assertion changes, repairing an accidental empty Query message, or repairing stale definitions after a real workflow edit.

For `model-generated` scenarios where `authoringHints.dataGuidance.baselineCompatible` is `true` (i.e., a base test file is available): before writing the scratch definition, read the base test file and locate the `testData.nodes` entry for each node listed in `authoringHints.dataGuidance.overrideRequiredNodeCodes`. Copy those node entries verbatim into `definition.testDataOverrides`, then modify only the fields needed to force the target branch outcome — for example set a collection field to `[]` for an empty-data scenario, or set a boolean/result field to `false` or `null` for a false-path scenario. When `branchForcingHints` says to establish conversation state through the workflow, preserve the compatible baseline, override only the listed recordable producer nodes, and let the existing transformation and SET_FIELDS nodes derive state normally. Do not inject prior-turn state or rewrite only `input.message` to bypass that path. Do not omit `testDataOverrides` when `overrideRequiredNodeCodes` is non-empty. For model-generated scenarios with `baselineCompatible: false`, generate complete `testData.nodes` entries for `requiredGeneratedNodeCodes`; do not use `testDataOverrides`. If you receive a CLI validation error, correct the scratch definition and retry. Do not count a CLI rejection as a failed attempt toward the 2-attempt unable-to-generate limit — only count attempts where the test was materialized and actually ran. A branch that can only be reached from conversation state established by an earlier turn is not a valid standalone single-turn scenario; cover it with a custom conversation test when requested.

Unable to generate sidecar: when one scenario could not be generated after 2 failed branch-forcing attempts or a live recording failure, first write `.debug/<test-name>-unable-to-generate.json` with the full payload (see schema below), then call `aistudio mark-workflow-test-unable-to-generate --file <wf> --blocker @.debug/<test-name>-unable-to-generate.json`. The CLI writes the blocker entry to `.debug/atlas-sync-blockers.json` with the current planning fingerprint and also deletes the test file from `test/workflows/` if it exists (for `path-divergence` type), so the scenario appears in Unable to generate in the final summary rather than Generated and failing. A blocker is ignored automatically when its scenario path, target branch, or capture policy no longer matches the current plan. The model must never write `.debug/atlas-sync-blockers.json` directly. Informing the user: deleting `.debug/atlas-sync-blockers.json` re-surfaces all unable-to-generate scenarios in the next sync plan.

After `mark-workflow-test-unable-to-generate` returns, the next output must be a tool call to `get-workflow-test-sync-plan`. Do not output any user-facing text, summary, or explanation between the blocker command and the sync plan rerun. After `get-workflow-test-sync-plan` returns `nextActionIds` during an active sync loop, the only permitted next step is executing the action listed in `nextActionIds`. Do not produce any text output, do not call `aistudio --help`, do not search for a batch command, and do not assess or mention the remaining action count. The remaining count is irrelevant — whether 1 or 51 actions remain, the next step is always executing the action in `nextActionIds`.

Phase 2 - Observe: run deterministic file-data validation to prove path assertions, exact RETURN assertions, replayed test data, and final-output availability. ## Flow Selection

- Static literal `RETURN` output: use `assertions.equals` directly when the whole return value is known. No observe pass is needed for exact static terminal messages.
- Semantic-output paths: do not auto-add output assertions. Initial definitions should include path assertions and judge metadata only. Add `contains`, `equals`, `startsWith`, or `endsWith` only when the user explicitly asks for that assertion or when an exact literal marker is explicitly specified as a workflow contract.
- Structural assertions must not be inferred from general behavior. For example, do not add `<html>` merely because the workflow appears to produce HTML, and do not add markdown fences, JSON braces, headings, labels, or section titles unless the exact literal boundary is explicitly required. If unsure, leave the structural assertion out for observe-first.
- When generating alternate static-return tests from a primary semantic-output baseline using `--base-test-file`, clear inherited structural assertions by including `"startsWith": null` and `"endsWith": null` in the definition passed to `do-update-workflow-test`.
- Future regression runs should use `--data-source file` unless the user explicitly asks for `live`. Do not invent `contains` values before seeing data.
- After observing recorded data for a primary-path collection-data presentation or summary, do not strengthen semantic-output terminal assertions from the observed final output. Leave semantic quality, formatting flexibility, derived presentation checks, names, periods, labels, meanings, section headings, and other wording-sensitive expectations to `judge.rubric` unless the user explicitly requests a literal assertion.
- Deterministic assertions must be literal, low-volatility substrings expected in the final output. Do not assert semantic concepts, section ideas, presentation wording variants, or source field names unless the user specifically required those exact words in the final output. If a deterministic assertion fails because of harmless wording or formatting variation, simplify or remove that assertion instead of chasing the new wording. Put semantic quality checks into `judge.rubric` instead. For exact static terminal messages, prefer `assertions.equals` so the whole final answer must match. Add `assertions.equals` only when the expected output is truly static, such as a literal `RETURN` node value or an explicit user-supplied exact assertion. If a `RETURN` node returns an expression like `{{$context...}}`, do not invent `assertions.equals` from the prompt; use stable `contains`, path assertions, and rubric checks unless the exact runtime value is explicitly provided and deterministic.
- User wants real env data now: prefer `--data-capture-policy record-now`.
- User wants structure now and data later: use `--data-capture-policy record-later`.
- User wants no env dependency or synthetic scenarios: use `--data-capture-policy model-generated`. When a ready recorded baseline exists for the same workflow, use `--base-test-file <ready-test-file>` plus `definition.testDataOverrides`; this preserves real node provenance and changes only the branch-forcing node outputs. Use a complete model-generated `testData` object only when no ready baseline exists. If every executable node must be synthetic, still use `--base-test-file` and override each executable node explicitly. Model-generated data must preserve response shape and include fields needed by downstream expressions, prompts, assertions, and judge rubric.
- Scenario changes only runtime trigger context, such as Agentic App `appHint` or REST trigger parameters, and the same recorded data path remains valid: use `--data-capture-policy baseline-replay --base-test-file <ready-test-file>` with an `input` definition and no `testDataOverrides`.
- If a representative `record-now` scenario fails because the live workflow takes a branch that violates `pathAssertions.mustNotExecute`, first apply the authoring, BO identity, input-binding, output-field, guard-expression, trigger-shape, and live-response checks above. Repair and retry once when an authoring defect is found. If the checks prove that required live data is genuinely unavailable, report the failed branch and missing condition as an environment-data blocker. Do not convert that same representative scenario to `model-generated` data without explicit user approval for intentionally synthetic coverage.
- Do not invent privacy, sensitivity, HR, payroll, performance, compensation, or employee-data blockers. A domain name, BO name, node name, or field label is not enough to claim live recording is blocked for sensitive data. Say live recording is blocked for privacy or sensitivity only when the user, CLI output, or an explicit policy says so. Otherwise report the actual blocker: missing input, unavailable environment data, fallback branch reached, remote draft mismatch, duplicate app-stage recording risk, or another concrete CLI/runtime reason.
- For app-stage tests with shared recordable data or the same LOOP boundary contract, prefer `InitDisplay` as the representative and record it from real data unless the user explicitly asks for a synthetic suite. Use `baseline-replay` for compatible Query, Summary, and other app-stage scenarios. Synthetic branch tests for fallback/error paths are allowed, but they must not replace the representative happy-path baseline.
- User asks for the whole flow: follow the single-action Sync Execution Contract. Execute the authoritative focused action, complete its data work, validate that affected test deterministically, and refresh the focused plan. Continue until `finalSummaryAllowed: true`, run one final canonical suite without `--run-label` and without overriding `evaluationMode`, attach canonical local judge results once without `--run-label` when requested, and use the rebuilt suite report without running the suite again. Run `--data-source live` only when requested.

For fallback, empty-data, and rare-branch tests, every node on the path from the trigger to the intended fallback terminal node must have a valid recorded or generated response in `testData`. Do not generate responses only for the terminal node. Each upstream BO, REST, tool, workflow, or session node whose output is checked by a branch guard must also have a valid response. For example, a "no related records found" test must give the upstream identity or parent-record node a valid `RecordId` so that guard passes, then make the downstream lookup node return an empty collection. If a fallback test routes to an earlier fallback, first verify that `testData` contains a valid response for the upstream node used by that earlier guard. Classify the issue as generated replay data precondition mismatch unless live recording also proves the upstream guard value is genuinely missing after guard expressions and trigger/input shape have been checked.

After a test exists, do not rerun `do-generate-workflow-test` with the same test name. The CLI refuses to overwrite existing test files. Use `do-update-workflow-test` to refresh the test for the current workflow while preserving valid `testData`, apply new model-produced data when the scenario requires it, or create a new test name for a genuinely different dataset.

All workflow test mutations must go through CLI commands. Do not manually patch final files under `test/workflows/` with `jq`, `sed`, Python, editor scripting, or shell redirection. For explicit user-requested assertion updates, write only the changed assertion definition fields to `.debug/<test-name>-assertions-definition.json` and run `aistudio do-update-workflow-test --file <workflow.wf> --test-file <test-file> --definition @.debug/<test-name>-assertions-definition.json` so validation, identity, ordering, and provenance rules are applied consistently.

Workflow test file names and `testName` are user-facing labels, not sync identity. Sync-plan generated tests use the persisted `scenario.id` as durable identity; custom user tests use `scenario.custom = true` and are not owned by sync-plan drift. To rename the report label or clarify test purpose, use `do-update-workflow-test` with only safe display metadata such as `{"testName":"new-display-name","scenario":{"intent":"What this test proves."}}`. Do not change `scenario.id`, `scenario.source`, `scenario.custom`, `scenario.kind`, or scenario-backed `pathAssertions` unless the current sync-plan action requires that update.

When creating or updating a sync-plan generated test from a plan action, include the plan action's scenario identity in the scratch definition if you include any scenario metadata. Use `scenario.id` from the action, write a concise `scenario.intent` in natural language, and keep `scenario.custom` absent or false. Do not derive sync identity from the file name or report label. For user-authored tests that are intentionally outside the sync plan, set `scenario.custom = true` and describe the custom intent.

For false-path, empty-data, rare-branch, and edge-case tests, use the sync plan's `baseTestFile` when it is present. Run `aistudio list-workflow-tests --workflow-code <workflowCode>` only when you are outside the sync loop and need a focused inventory. If no ready baseline exists and the environment can run the primary path, create/record the baseline first. When using `--base-test-file`, copy unchanged baseline nodes exactly except recordable nodes listed in `pathAssertions.mustNotExecute`; omit those skipped nodes from `testData.nodes` because they must not run. Do not relabel copied `raw` nodes as `model-generated`, and do not regenerate copied `model-compacted` nodes. Put only the minimum node responses needed to force the alternate scenario in `testDataOverrides`; those override nodes should normally use `capture.mode = "model-generated"`. `testDataOverrides` must be keyed directly by recordable node code and must never contain a `nodes` wrapper. Do not use `capture.mode = "raw"` inside `testDataOverrides`, and do not override nodes listed in `pathAssertions.mustNotExecute`.

Do not include `jobId`, `finishReason`, or `responseTruncated: true` on nodes with `capture.mode = "model-generated"`. Those fields describe runtime capture provenance; synthetic branch-forcing nodes should have `responseTruncated: false`.

## Scope

Current replay support covers workflows where recordable non-agentic data or workflow-boundary data comes from the explicit recordable allowlist: `BO_FUNCTION`, `EXTERNAL_REST`, `WORKFLOW`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, and `USER_SESSION`.

- Replay only the explicit recordable allowlist: `BO_FUNCTION`, `EXTERNAL_REST`, `WORKFLOW`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, and `USER_SESSION`.
- All other executable nodes run normally unless skipped by `pathAssertions.mustNotExecute`.
- Semantic-output nodes include `LLM`, `AGENT`, `MULTI_AGENT`, `WORKFLOW`, `RAG_DOCUMENT_TOOL`, and `DOCUMENT_PROCESSOR` when `extractWithLlm` is true. Generated tests for paths whose final output depends on these nodes should use path assertions and judge rubrics rather than generated deterministic final-output assertions.
- `WORKFLOW` is both recordable and semantic-output. Record and replay the child workflow boundary result in the parent test, keep child internals out of the parent assertions, and use hybrid judge coverage when parent final output depends on child workflow text.
- `VECTOR_DB_READER` test data uses `metadata: {}` and preserves the node's runtime response shape. Its fixed output is a top-level array of `{ index, text }` items, so downstream references use paths such as `$context.$nodes.SEARCH_POLICY_INDEX.$output[0].text`, not `$output.items[0].text`.
- `DOCUMENT_PROCESSOR` is replayable only when `extractWithLlm` is absent or false. When `extractWithLlm` is true, treat it as semantic output and do not include it in replayed `testData.nodes`.
- TOOL flavors are distinguished by the context `recordableNodeType`: deeplink-backed tools are `DEEPLINK_TOOL`, connector tools are `CONNECTOR_TOOL`, the ORA multi-file built-in is `MULTI_FILE_PROCESSOR`, the ORA user-session built-in is `USER_SESSION`, and `INTENT_CHANGE_INDICATOR` is not recordable.
- EMAIL uses normal node inputs such as `toList`, `subject`, `body`, `ccList`, and `attachments`. Do not look for or invent `emailAccountId`; preserve the EMAIL node's runtime response shape when recording.
- The no-generated-deterministic-assertion rule applies only to generated assertions. Preserve deliberate user-authored deterministic assertions even on semantic-output tests.
- Workflows with no replayable external-data nodes are still testable; their source-controlled test can have ready or pending `testData.nodes = {}` depending on the capture policy.
- Keep all source-controlled test definition and data for one scenario in the single test JSON file.
- Group workflow tests under the lowercase workflow code: `test/workflows/<lowercase-workflow-code>/<test-name>.json`.
- Reports are generated separately under `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.json`, `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.md`, `test-reports/workflows/<lowercase-workflow-code>/<test-name>/result.html`, `test-reports/workflows/suite-result.json`, `test-reports/workflows/suite-result.md`, and `test-reports/workflows/suite-result.html`. Reports are runtime output and should not live under the source-controlled `test/` tree.
- When presenting any report link to the user — suite report, per-test report, sweep report, or optimization report — always use the `.html` file path. Never present `.md` (Markdown) report links. The `.md` files are machine-readable intermediates; the `.html` files are the human-facing reports.
- Suite JSON reports include `summary`, `results[]`, `summaryText`, `optimization`, `nextActions`, and failed cases may include `failureSummary`; do not query old/nonexistent fields such as `stats` or `cases`. Use these fields plus the HTML reports to explain all-test runs clearly.
- Final user-facing responses after generating, updating, or running standalone workflow tests must use `get-workflow-test-final-summary --file <workflow-file>` as the evidence source for `Validation and Insights`. Put the workflow creation, change, or sync outcome first. Preserve test counts, the workflow suite report, `Metrics:`, and `Optimization:`. Include compact issue guidance when present; use `--format json` only when the user asks for detailed diagnostics. For run-only requests, do not use creation language.
- For tests that validate summaries or presentations over collection data, assertions and judge rubrics should check that the final answer preserves representative source records and downstream-relevant fields required by workflow intent. Do not accept purely anonymous aggregate output when the intent requires record-level grounding.
- Backend calls are allowed only for `do-record-workflow-test`, `run-workflow-test`, `run-workflow-tests`, and remote workflow freshness checks.
- The standalone CLI cannot invoke an assistant by itself; local model authoring happens before `--definition` or `--test-data` is passed to the CLI.

## Definition JSON Shape

Return exactly one JSON object when creating a definition. Do not wrap it in Markdown. Do not include `schemaVersion` or `kind`. Do not include fingerprints, hashes, external data files, or multiple datasets.

    "source": "model-authored",

    "dataSource": "file",

  },

For `EXTERNAL_REST` nodes, use `nodeType = "EXTERNAL_REST"` and stable metadata such as `externalRestToolCode` and `functionName` instead of Business Object metadata.

`workflow.workflowCode`, `testName`, and `authoring.createdAt` may be omitted from a definition. The CLI fills them from the local `.wf`, command options, and current time. Workflow status is a runtime target selected from the local `.wf` or `--workflow-status DRAFT|PUBLISHED`, not source test identity.

```json

      "UPSTREAM_RECORDABLE": {

    }

```

`testDataOverrides` is directly keyed by node code. Never wrap overrides in `nodes`.

Before running `do-generate-workflow-test` or `do-update-workflow-test`, verify the scratch definition locally: JSON parses, `testDataOverrides` is keyed directly by node code, no `testDataOverrides.nodes` wrapper exists, only branch-forcing nodes are overridden, skipped `mustNotExecute` nodes are omitted, unchanged baseline nodes are omitted, `capture.mode = "raw"` is not used in overrides, and `model-generated` override nodes do not include `jobId`, `finishReason`, or `responseTruncated: true`.

During workflow test-data recording, compaction, model-data generation, alternate-path baseline override creation, and judge/result handling, do not run catalog/discovery commands such as `search-business-objects`, `list-supported-business-objects`, `get-business-object-functions`, `get-bo-function-output-specification`, `search-deeplink-tools`, or connector/tool lookup commands. This restriction does not apply to workflow construction before test sync starts. If recording exposes a workflow metadata defect, classify it as a workflow defect and explicitly switch phases instead of hiding the lookup inside test-data compaction.

## Capture Policy And Runtime Data Source

- `--data-capture-policy record-later`: omit `testData`. The CLI creates `testData.status = "pending"`, `capturePolicy = "record-later"`, and node shells for every recordable node.
- `--data-capture-policy record-now`: omit `testData`. The CLI runs the workflow debug endpoint live and writes the test file with filled `testData` when each node response is complete valid JSON and within the size budget.
- `--data-capture-policy model-generated`: when no recordable nodes exist, the CLI can create ready empty `testData.nodes = {}` without a supplied `testData` object. Otherwise, either include complete `testData` with `status = "ready"`, `capturePolicy = "model-generated"`, and a response for every recordable node that can execute in the asserted path when no ready recorded baseline exists, or pass `--base-test-file <ready-test-file>` and include only `testDataOverrides` for the nodes that must change. Omit recordable nodes listed in `pathAssertions.mustNotExecute`. The local assistant generates this data from user intent and workflow context; the CLI validates it but never invents missing data. If a ready `record-now` baseline exists and a full `testData` object is supplied without `--base-test-file`, generation fails so real upstream node provenance is not lost.
- `--data-capture-policy baseline-replay`: pass `--base-test-file <ready-test-file>`, supply only the changed `input`/assertion/path/judge metadata, and omit `testData` and `testDataOverrides`. The CLI copies the baseline node data exactly, sets `testData.capturePolicy = "baseline-replay"`, and changes only runtime invocation context.
- `--data-source file`: replay embedded `testData`. This is the default for CI and local regression tests.
- `--data-source live`: call the environment and ignore `testData`. For LOOP scenarios, this validates live workflow behavior only; it does not prove boundary-output or single-iteration file replay, and a single-iteration scenario may execute the complete live collection.

## Smart Recording And Compaction

The CLI records raw data only when the captured response is complete, valid, not backend-truncated, unmodified, and small enough. Each recordable node response and each LOOP boundary output should stay around 2 KB to 3 KB. The implementation limit is 3072 bytes per artifact; the limit does not apply to `input`.

If recording sees backend-truncated output, invalid JSON, missing output, or oversized output for a recordable node or LOOP boundary, it must not write that output as ready test data. Instead it writes a workflow-backed request under `.debug/` and returns `needs-model-test-data`. Collect all usable run evidence before preparing the response; do not stop at the first oversized artifact.

For recorded data, keep runtime capture provenance under `capture`: `mode`, `responseTruncated`, optional `jobId`, and optional `finishReason`. Do not put `jobId` or `finishReason` in node `metadata`; `metadata` is for stable node identity such as `businessObjectCode`, `externalRestToolCode`, and `functionName`.

When that happens:

1. Read the request file, `decisionContext`, and all available run evidence.
2. Copy `replayDataPayloadTemplate` exactly. It contains only mutable node responses and LOOP artifacts.
3. Treat every `consistencyGroups` entry as one atomic decision. If row selection changes in a source response, update every correlated LOOP boundary or selected item in that group during the same apply.
4. Preserve every `rawArtifactsToPreserve` entry exactly from `testDataTemplate`. Never compact, regenerate, reorder, prune, or relabel it.
5. A legacy version 1 node-only request is one singleton node consistency group. Preserve its established behavior while using the same apply command.
6. Prefer fields referenced by downstream `CODE`, `LLM`, and `AGENT` nodes, assertions, and judge rubric.
7. Remove unused fields, large links, context metadata, and irrelevant nested data.
8. Preserve the response shape expected by the workflow.
9. For collections, prefer multiple narrow representative items over one wide item. When the request preview exposes multiple rows, keep 2 to 5 compact rows that preserve meaningful variety across fields the workflow actually uses, such as distinct categories, statuses, dates, numeric values, boolean states, or descriptive text.
10. Reduce fields before reducing record count. Drop downstream-irrelevant fields from all records before reducing the number of records. A field is downstream-irrelevant when no downstream CODE, LLM, or AGENT node prompt, expression, assertion, or judge rubric criterion references it. Only reduce record count if field reduction alone is still insufficient to meet the response budget.
11. For rating, scoring, or classification collection data where the workflow final output must represent each unique entity, compaction must retain at least one record from each distinct value tier of the primary metric that exists in the preview data. For example, if the preview shows primary metric tiers 1, 3, and 5, keep all three tiers represented even if only one record per tier survives. Dropping the highest or lowest tier removes grounding data and makes judge verification impossible.
12. Prefer fewer downstream-relevant fields across multiple rows over many technical fields from a single row. For LLM-consumed data, prioritize fields named in the LLM prompt, assertions, and judge rubric; drop `@context`, `links`, large IDs, and unrelated technical fields unless downstream logic explicitly references them.
13. Adjust envelope fields such as `count`, `limit`, `offset`, `hasMore`, and `links` to match the compacted collection. For compacted or generated collection snapshots, set `count` to `items.length`, set `hasMore` to `false`, keep `limit` greater than or equal to `items.length`, keep `offset` non-negative, and use an empty `links` array or omit links unless downstream logic consumes it.
14. Use `capture.mode = "raw"` only when the recorded response is complete, valid JSON, not backend-truncated, unmodified, and under the response budget.
15. For `record-now` requests, captured preview rows are real environment data. If any usable real row or field is present but the response cannot be stored as-is, keep `testData.capturePolicy = "record-now"` and use `capture.mode = "model-compacted"` for that node. Do not switch to `model-generated` merely because the preview is truncated or oversized.
16. For `model-compacted` collection data, first try to keep 2 to 5 real representative rows by trimming fields based on downstream usage and the response budget. Keep one real row only when multiple compact real rows cannot fit or cannot be reconstructed safely from the available preview/context. For a node with `capture.mode = "model-compacted"`, always set `capture.responseTruncated: true`. The CLI canonicalizes `capture.mode = "model-compacted"` to `capture.responseTruncated: true` during apply/create/update, but set it correctly up front. Model-compacted means the original response exceeded the response budget and was reduced; the stored subset never represents the complete environment response. `responseTruncated: false` is correct only for `raw` captured nodes (complete, unmodified, under-budget response) and `model-generated` nodes (synthetic data with no real environment source).
17. Use `capture.mode = "model-generated"` only when no usable real response rows or fields are available, or when the user intentionally requested synthetic model-generated data.
18. Treat `outputSpecification` as shape guidance, not a mandate to keep every property. Keep the collection envelope and downstream-relevant fields; omit schema-listed fields that downstream logic, assertions, and judge rubrics do not consume.
19. LOOP boundary output must remain `array<string>`, matching the runtime contract. JSON-looking iteration results remain strings inside that array.
20. Apply `replayDataPayloadTemplate` with `aistudio do-apply-workflow-test-data --test-file <test.json> --test-data @<prepared-data-file>` for workflow tests or `aistudio do-apply-app-test-data --test-file <test.json> --test-data @<prepared-data-file>` for app tests. When the recording result contains `temporaryTestDataPath`, write the prepared payload only to that exact CLI-managed path and pass it as `<prepared-data-file>`; the apply command removes its operation directory after success or failure. When no managed path is returned, retain the existing `.debug/<test-name>-test-data.json` or `.debug/app-tests/<test-name>-test-data.json` flow and add `--cleanup-scratch true` when the request and produced data files are no longer needed.

Never include backend-truncated `.....` previews in `testData`. Keep each node `response` and each LOOP boundary `output` around 2 KB to 3 KB or less.

## Recorded Data Masking

When the user asks to mask recorded names, identifiers, email addresses, or product-specific sensitive fields, let the user define the business scope in natural language. Do not rely on a fixed global list of HCM, SCM, CX, or other product fields. Before tests exist, run `get-test-data-masking-context --file <workflow.wf>` to inspect recordable node schemas and `existingProfiles`. After recording, `get-test-data-masking-context --test-file <test.json>` returns concrete scalar paths and value types without exposing values. When the user names fields, that list is authoritative: author rules only for those fields and do not add similarly named fields or semantic variants. When the user supplies only business categories, resolve them to the smallest applicable concrete field set. Only when no field scope is supplied may you infer a reasonable sensitive-field set from the available schemas. Use `nodeCodes: ["*"]` or recursive `**` paths only when the user explicitly requests the same field across all relevant nodes.

For a request that creates, changes, or reuses recorded-data masking, resolve masking setup before requesting a workflow or app sync plan that may load tests referencing that profile. First inspect masking context and `existingProfiles`; then reuse or create the named profile; only after the profile exists may you request the applicable sync plan. Do not run masking-profile setup and sync-plan commands concurrently. This ordering applies only to masking requests and does not change ordinary unmasked sync execution.

Before creating a profile, inspect `existingProfiles`. Reuse a suitable profile instead of creating a differently named duplicate. Once a profile exists, its rules are authoritative; do not broaden or replace them unless the user explicitly asks to change masking scope. For a new masked test family with no suitable profile, create one named profile before the first live recording with `do-create-test-data-masking-profile --file <workflow.wf> --profile @<profile.json>`. Put `dataMasking: { "schemaVersion": 1, "profile": "<name>", "rules": [], "exclusions": [] }` in every related workflow or conversation test definition before `do-record-workflow-test`. Keep the same profile reference on baseline replay and model-generated variants. The CLI masks live evidence before test data, LOOP evidence, compaction requests, recording attempts, assertions, or judge grounding are persisted. Baseline-derived tests inherit the base test's profile when the definition does not replace it.

For existing raw recorded data that has never been masked, run `do-mask-test-data --test-file <test.json> --profile <name> --dry-run true`, review only paths and counts, then rerun without `--dry-run`. Deterministic file replay is validated by default; the CLI restores the original file if validation fails. Use `--policy` only for an intentionally inline one-test policy. If the test already has `appliedPolicyHash` and the resolved policy changed, do not run `do-mask-test-data`; record fresh workflow or conversation data so masking is applied once to original runtime values.

Legacy profiles live under `test/masking-profiles/`. App-package profiles live under the nearest package-local test root at `tests/ai/self/<module>/masking-profiles/`. Tests may reference a profile and add narrow inline rules or exclusions. A reusable profile can contain rules for fields absent from a particular scenario; that scenario remains valid and retains the profile reference. Never add marker, placeholder, or schema-foreign fields merely to make a rule match. A selected field identifies sensitive source values; the same original scalar receives the same deterministic, type-compatible replacement across related workflow steps, app test data, node inputs and responses, LOOP selected items and outputs, URLs, assertions, and judge text. This consistency cascade does not broaden the profile's field scope. Invocation input is masked only by a rule that explicitly targets the reserved node code `$test`.

Never edit recorded values manually to simulate masking. Never write original-to-replacement maps into the test, report, profile, or `.debug/` files. For masking-enabled model data preparation, use only the `temporaryTestDataPath` returned by the recording command. Do not create another raw `*-test-data.json` file, place raw values in command arguments, or copy them into logs, reports, judge files, or unrelated scratch files. A changed referenced profile invalidates file replay and requires a two-step refresh: first update only the profile reference so the CLI clears old replay data, then record or generate fresh data in a separate action. Never submit old `testData`, `testDataOverrides`, or a previously masked conversation in the profile-changing update. For a conversation test, refresh the complete scripted conversation rather than mixing old and new step data. No `dataMasking` configuration means recording, generation, replay, reports, and sync behavior remain unchanged.

`.debug/` is temporary, gitignored local scratch space for authoring definitions, compaction requests, model-produced test data, and judge drafts. Masking-enabled prepared data uses the operation-scoped path returned under `.debug/atlas-sensitive-data/<operation-id>/test-data.json`; the CLI applies restrictive permissions and removes that operation after apply success or failure. Name other workflow-test scratch files with the test-name prefix, such as `.debug/<test-name>-definition.json`, `.debug/<test-name>-path-update-definition.json`, and `.debug/<test-name>-judge-result.json`, so `do-apply-workflow-test-data --cleanup-scratch true`, `attach-workflow-test-judge-results --cleanup-scratch true`, and `attach-workflow-test-judge-result --cleanup-scratch true` can remove them. A ready test must not depend on `.debug/`; the durable source of truth is only `test/workflows/<lowercase-workflow-code>/<test-name>.json`.

When cleaning up `.debug/` scratch files not covered by `--cleanup-scratch true`, such as BO search result files written with `--write-result`, scratch definition files, and compaction files, use shell `rm` to delete the files rather than editing them to empty content. Editing a file to empty can flood the conversation log with deleted JSON content. `do-apply-workflow-test-data --cleanup-scratch true` covers test-data request and response files; `attach-workflow-test-judge-results --cleanup-scratch true` covers judge-specific files. Remove any remaining scratch files with `rm .debug/<file>` or `rm .debug/*.json` at the end of the session.

Before running any git command such as `git status`, `git log`, or `git diff`, verify that a `.git` directory exists in the workspace root. If no `.git` directory is present, skip all git commands silently and omit any git-based workspace summary from the final response.

If `testData.status = "pending"`, the test was created with `record-later` or recording did not complete. Record real data with `aistudio do-record-workflow-test --test-file <test.json>` or apply model-produced test data before running with `--data-source file`.

## Node Assertions

Use optional `nodeAssertions` when the user wants to verify an intermediate node input or output, or when an intermediate data contract is important enough to protect independently of the final workflow response. Do not add them mechanically to every test. The model decides which node values carry business value; the CLI validates the metadata and evaluates it against completed runtime node events.

For a single-turn workflow or app test, place `nodeAssertions` at the test root. For a scripted conversation test, place them on the applicable conversation step. Each assertion requires a unique `id`, a short user-facing `name`, an exact workflow `nodeCode`, `target: "input" | "output"`, and an operator. `occurrence` defaults to `"last"` and may be `"first"`, `"last"`, `"all"`, or a positive one-based execution number.

Use RFC 6901 JSON Pointer in `path`. Use `decode: "json"` only when the selected value is one JSON string, or `decode: "json-array-items"` when the selected value is an array whose items are JSON strings. Apply `decodedPath` after that single explicit decode. Do not assume recursive parsing of nested strings.

Supported operators are `equals`, `notEquals`, `exists`, `notExists`, `type`, `contains`, `notContains`, `lengthEquals`, `lengthAtLeast`, `lengthAtMost`, `hasKeys`, and `hasOnlyKeys`. Exact object and array equality is deep and type-sensitive. Prefer structural operators such as `type`, `hasKeys`, or length checks when exact values are volatile. Use `equals` when the user explicitly wants the complete stable value verified.

Examples:

```json
{
  "nodeAssertions": [
    {
      "id": "normalized-request-shape",
      "name": "Normalized request has the required fields",
      "nodeCode": "NORMALIZE_REQUEST",
      "target": "output",
      "occurrence": "last",
      "operator": "hasOnlyKeys",
      "expected": ["category", "priority", "requestId"]
    },
    {
      "id": "active-item-count",
      "name": "At least one active item is returned",
      "nodeCode": "FETCH_ACTIVE_ITEMS",
      "target": "output",
      "path": "/items",
      "operator": "lengthAtLeast",
      "expected": 1
    },
    {
      "id": "decoded-status",
      "name": "Decoded response status is ready",
      "nodeCode": "BUILD_RESPONSE",
      "target": "output",
      "path": "/payload",
      "decode": "json",
      "decodedPath": "/status",
      "operator": "equals",
      "expected": "READY"
    }
  ]
}
```

Only target nodes present in the current workflow context. `START`, `END`, and legacy `ADD` nodes have no assertable runtime value contract. A `WHILE` node has no supported boundary output; assert a completed descendant instead. LOOP boundary outputs and completed LOOP descendants may be asserted when runtime emits them. For repeated nodes inside LOOP, WHILE, retry, or parallel execution, choose occurrence deliberately. Missing, truncated, or undecodable runtime evidence fails as unavailable evidence; never rewrite the workflow to accommodate a test-specific representation.

## Named Assertion Identity

For every newly authored assertion, use a stable lowercase kebab-case `id` and a concise business-facing `name`. IDs are persisted machine identity used for updates, result attachment, and JSON correlation. Names are the labels users read in human-facing HTML and Markdown reports; do not expose internal IDs there. Keep IDs unique across the complete test artifact, including output, path, node, widget, semantic rubric, conversation step, order, count, HUMAN, and WAIT assertions. Do not reuse one ID in another step or assertion category.

Output assertion objects use `value`, path assertion objects use `nodeCode`, semantic rubric objects use `criterion`, and widget assertion objects use `patternId`. App widget names should state the visible contract, such as "Message list is rendered", rather than repeat the raw pattern ID. Existing string entries remain valid legacy metadata. Preserve their shape during unrelated updates and never rewrite an existing test solely to migrate assertion metadata. New tests and newly added assertions should use named objects. Every new or changed semantic rubric item must include a meaningful business-facing name; the CLI rejects missing names and numbered placeholders instead of inventing a user-facing label.

Preserve an assertion's `id` when changing its name or expected value. A rename changes only `name`; a semantic edit changes the applicable `value`, `nodeCode`, `criterion`, `patternId`, or node-assertion contract without replacing the ID. When the user refers to the name visible in a report, read the current test and resolve that name to the persisted assertion using its assertion category plus node, step, or widget context when applicable. Preserve the resolved ID and update or remove only that assertion. If the same visible name remains ambiguous after applying that context, ask the user which assertion they mean. Never replace an ID merely because the user referenced the assertion by name. The CLI evaluates semantic values exactly as before, sends only criterion text to a semantic judge, and reattaches the matching ID and name to structured results.

Never author a bare numeric substring under `assertions.contains`, such as `"4"`. It can match unrelated numbers and is not a stable output contract. Use a context-bearing phrase such as `"4 instructions"`, use `assertions.equals` when the complete output is numeric, or use a numeric or collection `nodeAssertion` for an intermediate value. When an observed path refresh keeps a node in the same `mustExecute` or `mustNotExecute` bucket, preserve that path assertion's existing `id` and `name`; create a new identity only for a newly observed node or when the node changes buckets.

## Rules

- `defaults.dataSource` must be `file` or `live`; prefer `file`.
- `defaults.evaluationMode` must be `deterministic` or `hybrid`; prefer `hybrid` when final output depends on a semantic-output node and semantic evaluation is needed. Use `deterministic` for static-return tests whose `assertions.equals` fully verifies a fixed, hard-coded output string.
- `input` must be an object. `input.message` must be a string and may be empty for non-chat trigger types.
- `input.triggerType` is optional. Omitted or `chat` means normal chat-style execution. Non-chat values include `app`, `rest`, `email`, and `schedule`.
- `input.parameters` is optional and must be a JSON object when present. Use the debug API field name `parameters`, not `params`.
- `input.singleTurnOnly` is optional and must be boolean when present. Set it only when the matching run profile would set it, such as REST, email, or schedule invocations.
- `testData.status` must be `pending` or `ready`.
- `testData.capturePolicy` must be `record-later`, `record-now`, `model-generated`, or `baseline-replay`.
- `testData.loopReplay` is optional. `boundary-output` data is captured by the CLI. `single-iteration` data must provide one `selectedItem` for every LOOP listed by the scenario; recordable descendants continue to use the existing flat `testData.nodes` map.
- `capture.mode` must be `raw`, `model-compacted`, or `model-generated`.
- `assertions.contains` and `assertions.notContains` accept legacy strings or named objects shaped as `{ "id", "name", "value" }`. Use named objects for new assertions.
- `assertions.equals` is optional and should be used for exact whole-output checks, especially literal static fallback or early-return messages. It accepts a legacy string or a named object shaped as `{ "id", "name", "value" }`; use the named form for new assertions. Do not auto-add `assertions.equals` for expression-backed `RETURN` nodes because the exact runtime text comes from evaluated context.
- `nodeAssertions` is optional and verifies intermediate runtime node values. Preserve existing node assertions during unrelated updates. Add or change them only when the user requests intermediate validation or the scenario has a clear stable intermediate contract.
- `pathAssertions.mustExecute` and `pathAssertions.mustNotExecute` accept legacy node-code strings or named objects shaped as `{ "id", "name", "nodeCode" }`. Preserve sync-plan entries exactly when supplied. Use named objects for custom path assertions and other newly authored entries.
- App `widgetAssertions.requiredPatternIds` and `widgetAssertions.forbiddenPatternIds` accept legacy pattern strings or named objects shaped as `{ "id", "name", "patternId" }`. Use named objects for new widget assertions. Allowed patterns describe the panel contract and are not individual pass/fail assertions.
- `pathAssertions` may be omitted only for an existing custom single-turn test that intentionally has no structural contract. Every sync-plan-backed test and every conversation step must classify every executable workflow node exactly once across `mustExecute` and `mustNotExecute`. Use exact executable behavior node codes from the sync plan, `get-workflow-test-context`, or `get-workflow-test-scenarios`. Do not invent a test for a data state that has no distinct workflow route. Do not include structural workflow nodes in `pathAssertions`; the CLI ignores persisted workflow nodes whose type is `START`, `END`, or legacy `ADD`, plus `REFERENCEABLEBLOCK` definition roots. Runtime/debug events such as `NODE_START` and `NODE_END` are not workflow node codes.
- For sync-plan create/update actions, the sync plan's `expectedPath` is authoritative. When the visible action row includes `expectedPath`, copy it exactly into `definition.pathAssertions`; do not shorten it or omit `mustNotExecute`. When a focused next action exposes only `authoringHints` and omits the bulky `expectedPath`, omit `definition.pathAssertions` and preserve the scenario id or test name so the CLI rehydrates the full expected path from the sync plan. Never write empty, partial, or guessed `mustExecute`/`mustNotExecute` arrays to save tokens.
- For sync-plan `update` actions, do not preserve stale or narrower `pathAssertions` from the existing test. Use the current action's `expectedPath` when it is shown; otherwise omit `definition.pathAssertions` and let the CLI refresh it from the scenario id or test name. For a predicted model-generated scenario, repair input or test data while omitting `definition.pathAssertions`; do not replace the sync-plan path based only on a failed replay. If live execution proves a different path, stop and report the observed routing mismatch instead of silently changing a scenario-backed path.
- WHILE paths in the sync plan are topology-derived and represent the body-entering path. Do not infer a separate zero-iteration WHILE test from topology alone; create one only when the user explicitly asks for it or an observed run/debug result proves the body was skipped, and keep `pathAssertions` consistent with that observed path.
- Exhaustive `mustNotExecute`: for any alternate-path test, `mustNotExecute` must list every workflow node that will not execute on that path, including CONDITION nodes, all RETURN nodes for other paths, and all nodes downstream of the early-exit point. Do not limit `mustNotExecute` to only BO_FUNCTION and LLM nodes. Derive the complete list by tracing the workflow from the exit node to the end and listing every node that is bypassed, plus all sibling RETURN nodes that belong to other alternate paths.
- `judge.minimumScore` must be an integer from 1 to 5; prefer 4.
- `judge.rubric` accepts legacy strings or named objects shaped as `{ "id", "name", "criterion" }`. Use named objects for newly authored criteria. Do not include a rubric criterion that re-checks deterministic assertions such as "final answer satisfies the stable deterministic assertions", exact `startsWith` or `endsWith` boundaries, or exact `contains` values. Rubric criteria should cover semantic output-contract requirements that deterministic assertions cannot verify.
- Static-return judge rubric: when a test uses `assertions.equals` because the entire workflow output is a fixed, hard-coded string from a RETURN node, set `judge.rubric` to exactly one named criterion whose `criterion` is `"The workflow output exactly matches the expected static message for this error or boundary condition."` Do not use the multi-criterion LLM-output rubric for static-return tests. The `assertions.equals` check already covers correctness deterministically; the judge rubric must reflect what the judge is actually evaluating.
- `evaluationMode` for static-return tests: when a test uses `assertions.equals` because the entire workflow output is a fixed, hard-coded string from a RETURN node, set `defaults.evaluationMode` to `"deterministic"`. The `assertions.equals` check fully verifies correctness; a judge adds no additional coverage for a known static string and wastes tokens. Reserve `"hybrid"` for tests where final output depends on a semantic-output node and semantic evaluation is needed.
- `testData.nodes` must include every current executable recordable node (`BO_FUNCTION`, `EXTERNAL_REST`, `DEEPLINK_TOOL`, `VECTOR_DB_READER`, `VECTOR_DB_WRITER`, `DOCUMENT_PROCESSOR`, `POLICY`, `EMAIL`, `CONNECTOR_TOOL`, `MULTI_FILE_PROCESSOR`, or `USER_SESSION`) in the asserted path and must not include stale node codes. It may be `{}` when the workflow has no recordable nodes. A current recordable node may be omitted when listed in `pathAssertions.mustNotExecute` or when it is a descendant of a LOOP replayed in `boundary-output` mode; skipped nodes should have no fake placeholder data.
- Data node properties must be ordered as `nodeType`, `capture`, `metadata`, `input`, `response`.
- Use node codes exactly as shown in `get-workflow-test-context`.
- Use the workflow code namespace exactly as shown in `get-workflow-test-context`.
- Keep chat-style `input.message` short, user-facing, and concrete enough to invoke the workflow. For non-chat scenarios, preserve the sync-plan `suggestedInput` or active run profile trigger fields. Do not copy internal node prompts, `TASK:`/`OUTPUT:` prompt sections, workflow context expressions, test data, assertion text, or judge rubric text into `input.message` or `input.parameters`.
- Avoid assertions that depend on changing dates, IDs, or volatile wording unless the user's prompt explicitly asks for them.

## Judge Rubric Rules

`judge.expectedOutcome` must be a human-readable output contract description. Write `judge.expectedOutcome` as a self-contained description of what a high-quality final answer should contain and accomplish, derived from the workflow description and the original user request. Do not copy LLM node prompt text, TASK/OUTPUT sections, or unexpanded `{{$context...}}` runtime expressions into `expectedOutcome`. The judge evaluates actual final output text; unexpanded runtime expressions and raw prompt templates are not meaningful in that context.

Keep `judge.expectedOutcome` and `judge.rubric` logically equivalent. Before authoring them, make an internal inventory of mandatory final-output requirements from the scenario intent, original user request, explicit workflow output contract, and app or widget contract when applicable. Treat contributing terminal semantic-node prompts and system prompts as supporting implementation context, not independent authority for adding mandatory final-output requirements. Map every mandatory requirement to both the expected outcome and exactly one rubric criterion; the rubric must not weaken or strengthen that requirement. Keep each rubric criterion atomic and independently judgeable. Do not combine grounding, unsupported-claim avoidance, evidence-gap handling, recommendation quality, or other distinct obligations into one criterion. Preserve conjunction and alternatives exactly: an outcome requiring `A and B` cannot be represented by a criterion allowing `A or B`. Preserve conditional requirements as conditional: require evidence gaps to be identified when supplied evidence has gaps, but do not require an explicit no-gap statement unless the user-facing contract explicitly requires a status statement even when none exist. Do not turn general internal prompt guidance into an unconditional final-output requirement. Before calling the generate or update command, verify internally that each rubric criterion has a required source and a matching expected-outcome requirement. Do not persist this authoring checklist in the test file. Apply this rule when creating or explicitly refreshing a judge contract; do not rewrite an existing judge contract during an unrelated test update.

For any test where final output depends on a semantic-output node, always include an explicit `judge` block with a hand-authored `expectedOutcome` in the scratch definition passed to `do-generate-workflow-test` or `do-update-workflow-test`. Do not rely on the CLI's auto-generation from `--prompt` alone to produce `expectedOutcome`; the CLI may derive it from workflow metadata and include raw node prompt text with unexpanded `{{$context...}}` expressions. If `--prompt` was used without `--definition` for the initial scaffold, immediately follow up with a `--definition` update that includes a corrected `judge.expectedOutcome` before proceeding to the observe step.

After generation, immediately verify the persisted test file's `judge` block before cleanup can remove the scratch definition. If `judge.expectedOutcome` contains unexpanded runtime expressions, raw LLM prompt sections, or the auto-generated workflow-contract prefix, replace it with a self-contained plain-English output contract. If a deterministic test or a test with `assertions.equals` has more than one `judge.rubric` criterion, replace the rubric with the single static-return criterion. If a hybrid test has fewer than two substantive quality criteria, repair the judge block with criteria that cover the semantic output contract. Apply repairs through `do-update-workflow-test --definition`, not by hand-editing the test file. Skip the update when the persisted `judge` block already passes these checks.

For primary-path semantic-output tests, derive `judge.expectedOutcome` and `judge.rubric` from the workflow output contract: the workflow description, relevant semantic-output node prompts or descriptions, and the original workflow creation request when available. The expected outcome should summarize the complete output contract, not just the test generation prompt or a structural boundary.

Never add a redundant deterministic criterion. Criteria such as "Final answer satisfies the stable deterministic assertions", "Output starts with X and ends with Y", or "Output contains the expected values" duplicate checks that already ran before judge evaluation and must be omitted.

Write one independently verifiable criterion for each distinct semantic requirement that deterministic assertions cannot prove. Prefer criteria for content coverage, required sections or output categories, preservation of required entities/records/fields/transformations, and grounding against replayed `testData` and executed node results. Avoid vague criteria such as "output is well-formatted" or "output is useful" unless the workflow contract defines exactly what that means.

## Local Judge Result Contract

An ordinary readable local judge request with an attach command is never a concrete blocker. For an explicit single-test hybrid request, complete only that test: read its request, evaluate its final output, write its matching judge result, and use the targeted singular attach command. For a workflow sync or final workflow suite, collect every local judge request from that suite, write all matching results, and attach them once with the plural suite command. Judge attachment alone does not change generation state and does not require a sync-plan refresh or suite rerun. Classify judging as blocked only after attempting the applicable continuation and finding that a request cannot be read, a result cannot be written, or the attach command fails.

`hybrid` evaluation runs deterministic assertions first. With the default `local` judge provider, if deterministic checks pass, the CLI writes `.debug/<test-name>-judge-request.json` for normal runs or `.debug/workflow-test-runs/<safe-run-label>/<test-name>-judge-request.json` for run-labeled model comparison runs, marks the run `needs-judge`, and prints the attach command. In that default route, the CLI does not call an LLM, the live environment, the workflow debug API, or a backend Builder API for judging. The assistant must read the request, evaluate the final output against `judge.expectedOutcome` and `judge.rubric`, and write the matching `<test-name>-judge-result.json` next to the request file. For an ordinary workflow sync suite, use `aistudio attach-workflow-test-judge-results --workflow-code <workflowCode> --cleanup-scratch true` without `--run-label`. Add `--run-label <label>` only when attaching a suite that was intentionally run-labeled for model comparison, optimization, or an explicit user request. For an explicit single-test run, use the targeted singular attach command printed for that report and do not judge unrelated suite tests. The CLI attaches the applicable judge results and rebuilds parent suite JSON, Markdown, and HTML from individual reports. Treat the suite report rebuilt by attachment as authoritative when it reports 0 failed and 0 needs-judge; do not run another default/hybrid suite pass just to confirm the attach. Judge results can be attached only to pending `needs-judge` hybrid reports.

When `run-workflow-test` or `run-workflow-tests` uses `--judge-provider remote`, the CLI still writes the judge request file for audit, then calls the configured FA environment, validates the returned judge JSON, writes the matching judge result file, and marks the test passed or failed in the same run. Remote judging uses the environment default model; do not pass judge model overrides or try to select a judge model.

When attaching a local assistant judge result, write strict JSON with exactly this accepted shape. The array field must be named `criterionResults`; names such as `rubricResults` or `results` will be rejected. `unsupportedClaims` must always be present as an array; use `[]` when there are none. Top-level `passed` must be `true` when `score >= minimumScore` from the test file, and `false` otherwise. Include one `criterionResults` entry for each criterion in `judge.rubric`. Do not use a top-level `findings` array instead of `criterionResults`.

Before writing `.debug/<test-name>-judge-result.json`, self-check all five required top-level keys: `score`, `passed`, `summary`, `criterionResults`, and `unsupportedClaims`. The field names `criteria`, `rubricResults`, `results`, and `findings` are wrong and will cause attach to fail; per-criterion details belong in `criterionResults` entries. `unsupportedClaims` must always be present as an array, even when empty (`[]`). Inside each `criterionResults` entry, use `criterion`, `passed`, and `notes`; do not add a per-criterion `score` field. Start from the `judgeResultTemplate` in the judge request file and fill in the values instead of constructing the shape from memory.

```json
{
  "score": 5,
  "passed": true,
  "summary": "The final output satisfies the judge rubric and stays grounded in the replayed workflow data.",
  "criterionResults": [
    {
      "criterion": "<criterion text from the test rubric>",
      "passed": true,
      "notes": "<brief justification>"
    }
  ],
  "unsupportedClaims": []
}
```
